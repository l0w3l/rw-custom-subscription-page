# Объединение подписок по Telegram ID

Функция предназначена для Remnawave 3.1+ и включается на сервере страницы подписки:

```dotenv
CUSTOM_SUB_PREFIX=sub
TELEGRAM_SUBSCRIPTION_MERGE_ENABLED=true
```

После изменения `.env` пересоздайте контейнер страницы. При сборке этого форка через локальный `docker-compose.yml`: `docker compose up -d --build`; frontend и backend собираются внутри Docker. API-токен должен иметь права чтения пользователей `by-short-uuid` и `stream`. Токен остаётся на сервере.

Клиент продолжает использовать `https://domain.example.com/sub/{shortUuid}`. Формат ответа выбирает Remnawave по исходным заголовкам клиента. Также работают штатные суффиксы `/mihomo`, `/clash`, `/json`, `/v2ray-json`; их фактический формат определяется настройками панели. Xray — движок: обычная ссылка `/xray` в контракте Remnawave не предусмотрена.

## Поиск и приоритет

1. Страница получает исходный ответ панели и пользователя через `GET /api/users/by-short-uuid/{shortUuid}`.
2. Для положительного Telegram ID получает все страницы `GET /api/users/stream?telegramId={id}&size=250`, передавая `nextCursor` как `cursor`. Дополнительно проверяет точное совпадение Telegram ID локально.
3. Оставляет пользователей со статусом `ACTIVE`, будущей датой окончания и неизрасходованным трафиком. Лимит `0` означает безлимит.
4. Первой идёт активная подписка из URL, затем остальные по `createdAt` от старых к новым; при равной дате — по числовому `id`.
5. Для каждой подписки получает конфигурацию панели с теми же User-Agent, HWID, IP и явным типом клиента.

При совпадении хоста сохраняется конфигурация первой подписки, включая её учётные данные. Новые хосты добавляются в порядке приоритета. Хосты сравниваются по конфигурации endpoint/протокола/транспорта без пароля, UUID и отображаемого имени. Различающиеся транспорты и настройки TLS остаются отдельными вариантами. В Xray единица объединения — целый профиль с `outbounds`: правила, DNS и цепочки outbound внутри профиля сохраняются вместе.

Если подписка из URL стала `LIMITED`, `EXPIRED` или исчерпала трафик, её хосты исключаются и используются оставшиеся активные подписки. Это происходит **при следующем обновлении подписки клиентом**, а не во время текущего соединения. Держите автоматическое обновление подписки включённым в клиенте.

Пользователь `DISABLED` не открывает доступ к связанным подпискам. Ответ с запретом HWID также не объединяется. При отсутствии Telegram ID или активных подписок остаётся исходный ответ панели. Изменение/удаление Telegram ID в панели меняет состав объединения при следующем запросе.

## Приоритет хостов в клиенте

В начале имени/remark хоста в Remnawave поставьте `[P<number>]`, например:

```text
[P1] 🇩🇪 Germany
[P10] 🇳🇱 Netherlands
🇫🇮 Finland
[P2000] Backup
```

В выдаче клиенту хосты будут расположены в указанном порядке, а префиксы исчезнут:
`🇩🇪 Germany`, `🇳🇱 Netherlands`, `🇫🇮 Finland`, `Backup`.

- Меньшее целое число означает более высокую позицию; `0` допустим.
- Без маркера приоритет равен `1000`. `[P2000]` располагается ниже обычных хостов.
- При равном числе сохраняется прежний порядок, включая приоритет подписок.
- Маркер распознаётся только в начале имени, с заглавной `P`, и должен оставлять
  непустое имя. Отрицательные/дробные числа и некорректные маркеры не обрабатываются.
- Дубликаты сначала разрешаются по приоритету подписок. Затем выполняется сортировка
  хостов: `[P1]` у дубликата из второй подписки не заменяет ключи из первой подписки.

Работает для Xray JSON (`remarks`), ссылок URI/Base64 (имя после `#`), VMess (`ps`),
Mihomo/Clash (`proxies[].name` и inline provider `payload`). В Mihomo сортируются также
списки выбора `proxy-groups[].proxies`; ссылки на переименованные хосты в группах,
правилах, `dialer-proxy`, туннелях и настройке `proxy` провайдеров обновляются.
При совпадении очищенных имён добавляется `(2)`, `(3)` и т. д. Имена групп сохраняются.
Порядок узлов внутри `relay` и Xray `outbounds` сохраняется: это цепочки маршрутизации.

Обработка применяется к скачиваемой конфигурации после объединения, в том числе к
одиночной подписке и при `TELEGRAM_SUBSCRIPTION_MERGE_ENABLED=false`. Дополнительная
настройка `.env` или права API не нужны. Без маркеров ответ не меняется.
HTML-страница и сами названия в панели сохраняют исходные маркеры.

Непрозрачные SSR-ссылки, зашифрованные подписки и содержимое внешних HTTP/file providers
не обрабатываются. Если шаблоны используют регулярные выражения для фильтрации имён,
они должны учитывать уже очищенные имена. Приложение может включать собственную
сортировку: для отображения этого порядка выберите исходный порядок подписки.

## Форматы

- **Xray JSON:** объединяются массивы полных профилей; одиночный объект тоже принимается. Дубли сохраняют настройки первой подписки.
- **URI / Base64:** объединяются строки ссылок, сохраняется способ кодирования. Поддержаны VLESS, VMess, Trojan, Shadowsocks, Hysteria/Hysteria2 и TUIC. SSR сохраняется как непрозрачная строка, удаляются только точные дубликаты SSR.
- **Mihomo / Clash YAML:** объединяются `proxies`, ссылки в `proxy-groups` и `payload` inline proxy providers. При одинаковом имени у разных хостов добавляется суффикс `(2)`, `(3)` и исправляются ссылки из групп. DNS, rules и прочие общие параметры берутся из первой активной подписки. У групп с одинаковым именем настройки первой группы имеют приоритет, списки `proxies` и `use` дополняются.

Разные внешние proxy providers под одним именем и неоднозначные `dialer-proxy` не объединяются: возвращается исходная подписка. Это также относится к ошибке API, некорректному ответу, смешению форматов, Sing-box и зашифрованным ответам (например, Happ). Конфигурации разных подписок должны использовать совместимые шаблоны; общие правила из последующих шаблонов не переносятся.

## Метаданные и ограничения

Заголовки профиля, название и ссылки поддержки сохраняются от исходной подписки. `subscription-userinfo` пересчитывается для вошедших в объединение активных аккаунтов: сумма использованного трафика и лимитов, максимальная дата окончания; при наличии безлимита `total=0`. Это сводка аккаунтов, а не общий баланс каждого отдельного хоста. Служебные заголовки длины, контрольной суммы и кеширования тела пересчитываются/удаляются. Ответ объединения получает `Cache-Control: no-store`.

HTML-страница и её карточка статистики показывают исходную подписку. Объединение применяется к скачиваемой конфигурации и её HTTP-заголовкам; индивидуальные ключи на HTML-странице относятся к исходному аккаунту.

Включение функции означает, что ссылка одной подписки открывает доступ к активным подпискам с тем же Telegram ID. Назначайте общий ID только аккаунтам одного владельца. Отдельного кеша учётных данных нет. На запрос выполняется поиск пользователя, пагинированный поиск связанных аккаунтов и последовательная загрузка их подписок; учитывайте нагрузку и время ответа при большом количестве аккаунтов.

## Проверка

Если появляется `Subscription aggregation failed`, строка лога содержит JSON с этапом
`stage` и причиной `reason`. Токены, Telegram ID, идентификаторы подписок, тела ответов
и ключи прокси не выводятся. `subscriptionIndex` — позиция подписки в порядке приоритета,
начиная с 1, а `activeSubscriptions` — количество активных подписок.

- `panel_request_failed` и `httpStatus: 401/403`: проверить API-токен и его права на
  endpoints пользователей. На этапе `fetch-subscription` проверяйте доступ к endpoint
  подписки и правила панели для клиента.
- `invalid_panel_response` и `fields`: ответ API не содержит корректных данных в
  перечисленных полях. Теперь проверяются только данные, необходимые для объединения;
  формат `vlessUuid` из Remnawave 3.4.4 не проверяется старой схемой SDK 3.1.1.
- `format_mismatch`: исходная и связанная подписки отданы в разных форматах.
  В логе указаны ожидаемый `format` и `receivedFormat`; проверьте шаблоны/SRR для аккаунтов.
- `hwid_restricted`: панель запретила связанную подписку этому устройству.
- `conflicting_external_providers` или `conflicting_dialer_proxy`: конфликт шаблонов Mihomo.

Пример диагностического сообщения: `{"stage":"get-related-users","format":"mihomo","reason":"panel_request_failed","httpStatus":403}`.

```sh
cd backend
npm ci
npm test
npm run typecheck
NODE_ENV=production npm run build
```

Тесты используют синтетические конфигурации и замоканный API, проверяют приоритет, лимиты/сроки, пагинацию, заголовки, HWID, YAML-ссылки и восстановление исходного ответа при ошибках. Перед развёртыванием проверьте импорт собственных шаблонов в используемые приложения: живой экземпляр панели и клиенты не входят в эти тесты.
